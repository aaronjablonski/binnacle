# Mission Control: developer-experience ideas beyond v1

Date: 2026-11-15. Research and design only; nothing here is built or planned.
"TF n" is a line in `mod/.claude-plugin/types/claude-code/index.d.ts`
(Claude Code 2.1.325). Effort: S is about a day, M two to three, L a week.

Every idea keeps the anti-goals unless its "Risks" line says otherwise: hooks
observe and return `next(e)` unchanged, no model call, state stays bounded.
None of the eleven needs a model call. Three touch the conversation only when
the person presses something (marked **person-initiated**).

Mocked: ideas 1 to 4, as `Idea1.dc.html` to `Idea4.dc.html` in the mock
canvas folder (`…/scratchpad/mcstyles/project/`).

## 1. Needs-you queue (M)

**Sees and does.** A `NEEDS YOU` section at the top of the Overview, shown only
when it has rows, and a band that changes from calm to an error-coloured count
(`! 2 need you`). Four kinds of row:

- *Permission wait*: a step that the permission check sent to the person and
  that has not ended, with how long it has waited and which agent asked.
- *Repeat failure*: the same call signature (tool plus normalised argument)
  failed two or more times.
- *Loop*: the same signature ran three or more times in one turn, failed or not.
- *Stalled agent*: an agent is running but has started no step for N minutes
  (default 3), or `$.agent.list()` reports it `waiting`.

Pressing a row opens the step or the agent. Each row has a dismiss key; a
dismissed signature stays quiet until it grows. If the terminal is not being
watched, one native notification is raised per new permission wait or turn that
ended in an error (opt-in, `notify: 'off' | 'waits' | 'all'`). A toast is used
for softer events: an agent finished, with the first line of its answer.

**Why.** It answers the question a developer actually has when they look over:
"is it stuck, and is it stuck on me?" Today a subagent waiting on a permission
prompt or looping on a failing test looks the same as one working.

**API.**
- Permission wait: observe `tool.check` (TF 4289; input TF 14794 carries
  `tool_use_id`, `agentId`, `approver`); `const r = await next(e)` and
  `r.decision === 'ask'` (TF 14857) marks the step as asking. The step ends
  through the existing `tool.call` capture. `classic.PermissionRequest`
  (TF 8158) and `classic.Notification` (TF 7201) confirm the dialog is up.
- Repeat and loop: pure model work over `Step.label` plus status; the
  signature rule is the one proven in the extension's `problems.ts`.
- Stalled: the existing one-second `$.clock.every` (TF 3716) compares
  `now - lastStepAt`; `AgentStatus` has `waiting` (TF 586) via
  `$.agent.list()` (TF 3439; not workflow agents).
- Turn ended badly: `turn.complete` `reason: 'error' | 'refusal'` (TF 15440).
- Delivery: `$.ui.notify` (TF 2548; options TF 7210), `$.ui.toast` (TF 2525),
  and `PromptHint.tail` (TF 11332) for a dim `! 2` when the band is collapsed.

**Risks.** `tool.check` resolves to the engine's decision, not the person's
answer, so "waiting on you" really means "asked and not finished"; a long tool
the person already approved reads as waiting until it ends. No event reports
the person's answer, so the row says `asked 40s ago`, not `waiting`. One unmatched `tool.check` hook per
module. Notifications can nag: default to `waits` only, one per step, and never
for a wait shorter than 20 s. Claude Code raises its own permission
notification; ours must not double it (key on `notification_type`).

## 2. Find and jump (M)

**Sees and does.** Two halves of "finding things fast".

- *Find.* The Timeline gets an `Input` on top: type `429` or `rateLimit.ts` and
  the list narrows as you type, across tool, label, path, agent and pin note.
  `/mc find <text>` does the same from the prompt mid-turn, without pane focus.
  Filter chips next to it: All, Pinned, Errors, Changes, one agent.
  Enter on the field runs a deep search over stored step bodies (result text)
  and marks hits `in result`.
- *Jump.* Every step row and the step detail get `Show in chat`: the transcript
  scrolls to that tool's own row and centres it. In the Agents tab, `View`
  switches the main view to that agent's transcript. In the other direction,
  steps whose rows are on screen right now carry a dim `◂ on screen` mark, so
  the Timeline shows where the transcript is.

**Why.** This is the mod's founding complaint ("that step from ten minutes
ago"). v1 lets you reopen a step in the pane; it does not take you back to the
place in the conversation, and it has no text search.

**API.**
- `Input` with `onInput` and `onSubmit` (TF 5866); `/mc find` through the
  existing `immediate` command (TF 1984).
- Deep search: `$.fs.read` (TF 3494) over the journal's step files, newest
  first, capped (200 bodies, stop at 8 s of the 10 s hook budget).
- Jump: `$.ui.scroll({ to: { requestId: step.id }, block: 'center' })`
  (TF 2653, 16463, 16641). A `ToolUse` row's `requestId` is the `tool_use_id`
  (TF 10956), which is the step id. Allowed because the call answers the
  person's own press.
- Agent transcript: `$.ui.view({ agentId })` (TF 2714, 13307), also only on a
  press; `Pane` props `view.agentId` (TF 11503) can preselect the agent filter.
- On-screen mark: `ToolUse` props `onScreen` (TF 10956), read in an observing
  `ui.render` hook that returns `next(e)` untouched and stores the visible ids
  in a module variable (not `$.state`: render may not write state).

**Risks.** The engine moves a transcript row "only where one scrolls": this is
a fullscreen-terminal feature; elsewhere the button must hide or say why
(`{ deny }`). Rows folded into a `ToolGroup` (TF 11078) may have no row of
their own to scroll to. The `onScreen` observer runs for every tool row, the
site the spec calls riskiest; it draws nothing, but it must be cheap and must
never throw. Deep search reads files inside a 10 s hook.

## 3. Budget line (M)

**Sees and does.** One `BUDGET` section in the Overview: context window fill as
a block bar, the rate-limit windows with their reset time, and session time.
The Agents tab gains two dim columns per agent: model and tokens, with a
per-model total row (`opus 212k · sonnet 96k`). A toast at 80% context and at
each 10 points of the five-hour window past 70%. Sort agents by tokens with
one key.

**Why.** Aaron's own rules are about quota (which model runs what, and how fast
a window drains). The pane already knows every agent; adding which model it
ran on and what it spent turns "Opus plans, Sonnet executes" into something
visible while it happens, in time to stop a runaway agent.

**API.**
- `session.measure` (TF 4748; input TF 12444): `context` (TF 12238),
  `rateLimits[]` with `percentUsed` and `resetsAt` (TF 12631), `cost.usd`
  (TF 12268), and `changed` to redraw only when something moved.
  `$.session.usage()` (TF 3045) for the first reading; the plain call is free.
- Per agent: `turn.complete` carries `agentId`, `durationMs` and `usage`
  (TF 15383) with the model id (TF 15794) and token counts (TF 6927).
  The model an agent was given is on the `agent.spawn` result (TF 442).
- `Progress` (TF 8786) or the restyle's block bar; `$.ui.toast` (TF 2525).

**Risks.** The spec lists "cost analytics" as a non-goal. This stays inside it
by being one section and two columns, with no charts, history or dollar
breakdown; `cost.usd` is shown only if the person turns it on. Workflow agents
report usage through `turn.complete` like any agent, but that needs a fixture
to confirm. Tokens for an agent still running are unknown until its turn ends:
show `…`, not zero.

## 4. Resume card and session history (M)

**Sees and does.** On a new session in the same project, the Overview opens
with `LAST TIME`: when the last session ended, its final focus and next line,
its open tasks, pins and notes, and its artifacts. Keys: open that session's
timeline read-only, copy the card, or put it into the prompt as a draft.
`/mc history` lists the last 20 sessions for this project, each one line; any
can be opened read-only (pins, notes, steps and their bodies).

**Why.** The record is the mod's best asset, and today it dies with the
session. "What was I doing here on Friday, and what did Claude find out?" is
answered with no model call and no re-reading of a transcript.

**API.**
- Index: `$.store.set('sessions', …)` (TF 3618, 4 MiB across sessions): per
  session the id, project root (`$.session.root()`), start and end, first
  prompt, last focus and next, counts. Written at `turn.complete` and
  `session.end` (TF 4760).
- Content: the journal already writes `timeline.json` and step files per
  session; `$.fs.read` (TF 3494) and `$.fs.list` (TF 3515) load an old one.
- Draft: `$.prompt.fill({ text, mode: 'insert' })` (TF 3200, 9421).
- Copy: `$.ui.copy` (TF 2683).

**Risks.** **Person-initiated conversation change:** "Use as prompt" puts text
in the composer; the person still has to press Enter, and the mod never
submits. It must not auto-inject context at `session.start` (that would be a
second thing the mod adds to conversations). Journals are pruned to 20
sessions, so the index must be pruned with them. A read-only timeline needs a
clear banner so nobody takes old state for live. Old notes can be wrong by
now; show their age.

## 5. Handoff (S)

**Sees and does.** `/mc export` (and a key on the Overview) writes
`mission-control-<date>.md` to the project: tasks with status, notes, pinned
steps with their input and a cut of the result, artifacts with links, files
changed, and open errors. The same text goes to the clipboard. In step detail:
`Copy as Markdown` (tool, input, result in fenced blocks) and `Quote in prompt`
(the result, or the selected part, as a `>` quote in the draft).

**Why.** Handing a finding to a colleague, a PR description or the next session
currently means scrolling and selecting terminal text by hand.

**API.** `$.fs.write` (TF 3501; build the path from `$.session.root()`),
`$.ui.copy` (TF 2683; check `isCopied`), `$.prompt.fill` (TF 3200),
`Link` (TF 6063) for artifact URLs.

**Risks.** The digest is a template over the model, not a summary, so it is
only as good as Claude's notes. It writes a file into the repo: ask for the
path once, default to a git-ignored folder. Step bodies can hold secrets
(`.env` reads): the export lists pinned steps only, never every body.
**Person-initiated:** `Quote in prompt` fills the draft.

## 6. Pin what you selected (S)

**Sees and does.** Select text in the transcript with the mouse, type
`/mc pin`: the step whose row holds the selection is pinned, with the selected
text as its note. With no selection, `/mc pin` pins the latest step as today.

**Why.** Pins are goal 4, and the natural moment to pin is while reading the
thing in the transcript, not after finding it again in the pane.

**API.** `$.ui.selection()` (TF 2697; `requestId` is the row's `tool_use_id`,
TF 16693), then the existing `pin` event.

**Risks.** No selection is reported outside fullscreen or when it spans rows;
fall back to the latest step and say so in the command's reply. A selection in
an assistant message has no step: keep it as a note instead.

## 7. Keyboard flow without pane focus (S)

**Sees and does.** The main verbs work from the prompt: `/mc find`, `/mc pin`,
`/mc next-error`, `/mc agent <name>`, all `immediate`. One engine chord, chosen
by the person in settings, toggles the pane. Inside the pane: `autoFocus` on
the row most likely wanted (the newest error, else the running step), `n`/`p`
step through errors, `g` jumps to the transcript, `Esc` hands the keys back.
Key hints show only while the pane has focus.

**Why.** Keys reach a pane only when it has focus, so every feature that needs
focus first costs a chord. Commands and one bound action remove that cost for
the common cases.

**API.** `immediate` commands (TF 1984); `ButtonProps.action` (TF 1147): an
engine keybinding action's chord presses a mounted Button from the prompt;
`hotkey` (TF 1140); `autoFocus`; `$.ui.focus` (TF 2669); `Pane.isFocused`
(TF 11503).

**Risks.** A mod cannot define a new action, only borrow one, and only while
no engine handler for it is mounted; the choice of action must be a config
value with no default. A pane closed by the chord has no mounted Button to
reopen it, so the toggle Button has to live in the band.

## 8. Workflow run board (M)

**Sees and does.** Opening a run in the Agents tab shows one row per workflow
agent: index, description, status glyph, a strip of small blocks (one per
step, coloured by status, the running one in the warning colour), elapsed, and
its result line taken from its `StructuredOutput` call. A header gives
`4/6 done · 1 failed · 6m`. Rows are in spawn order, so phases read top to
bottom. Pressing a block opens that step.

**Why.** Workflow agents answer with an empty `turn.complete` (Findings d), so
today a finished workflow agent shows nothing useful. The run is the unit a
developer thinks in.

**API.** `agent.spawn` `workflow: { runId, agentIndex }` (TF 281, 4409), the
`Workflow` call's result (`workflowName`, `runId`), `tool.call` for
`StructuredOutput` with the agent's `agentId` (TF 4275). Drawing is `Text`
runs inside a `Button` (strings and `Text` only).

**Risks.** The spec's v1 non-goals name "waterfall"; this is a step strip, not
a time-scaled waterfall, but it is the same family and needs Aaron's yes.
There is no workflow-run event, so the planned agent count (`n/m`) is known
only if the workflow's own result states it. Phase names are not in any event.

## 9. Transcript marks on tool rows (M)

**Sees and does.** Tool rows in the transcript that Mission Control knows
something about get a dim tail on their own line: `★ pinned · the limiter
itself`, `x3 same failure`, `12.4s`. Rows with nothing to say are returned
untouched. A pinned row could carry a small `unpin` button, and an errored
one `open in /mc`.

**Why.** It ties the two halves of the screen together: you see in the chat
that a step is pinned or is the third identical failure, without looking at
the pane.

**API.** `ui.render` on `{ component: 'ToolUse' }` (TF 10956), keep-and-add:
`const theirs = await next(e)`, then a `Box` holding `theirs` and one `Text`.
Pass through when `isExpanded`. Buttons in a tool row raise `ui.press` with
`component: 'ToolUse'` and the row's `requestId`.

**Risks.** **Brushes the non-goal** "changing how the transcript itself is
drawn": this adds one line under a few rows and collapses nothing, but it is
the riskiest site (every row asks the hook, a bad tree draws nothing for that
row). One unmatched `ui.render` hook per module, and the guide already hooks
`ToolUse` with a matcher for its own tool. `ToolUse` has no `bodyColumns`
(Findings, Task 4), so the tail is cut to `viewport.columns`. Do this after
idea 2's observer has proved the site is safe.

## 10. Review queue: changes by file (L)

**Sees and does.** A `Changes` filter in the Timeline groups Edit and Write
steps by file: path, `+38 -4`, number of edits, which agents touched it. Opening
a file shows its edits in order as diffs, with a `Reviewed` toggle per file; the
Overview's `4 files` becomes `4 files · 1 reviewed`. A key copies the path.

**Why.** After a long run the developer's job is review. The transcript shows
edits in the order they happened, interleaved with everything else; a reviewer
wants them by file.

**API.** `Timeline.changed` and the journal's step bodies; `Code` with
`format: 'diff'` (TF 1692); `$.ui.copy` (TF 2683). Optional ground truth from
`$.process.run(['git', 'diff', '--stat'])` (TF 3786).

**Risks.** The spec rejected a Files tab because it "would blow up"; this is a
filter with a cap (the 30 most recently changed files), not a tab. Diffs built
from Edit inputs are per edit, not the net change; a net diff needs git, which
means running a process (read-only, but new ground for this mod). `Code` takes
100,000 characters per drawing, so only one file's edits draw at a time.

## 11. Agent tree, upgraded (S)

**Sees and does.** The existing text tree gains per-node dim meta (elapsed,
steps, tokens from idea 3), a `!` on a stalled or failed node that also shows
on its folded ancestors, a count on a folded branch (`▸ 4 agents · 1 running`),
and `View` to open that agent's transcript. A `running only` toggle hides
finished branches.

**Why.** Deep trees (an orchestrator, its implementers, their reviewers) are
where a developer loses track; the problem node should be visible even when its
branch is folded.

**API.** Model selectors only (`agentTree`, `treeLines` in `select.ts`), plus
`$.ui.view` (TF 2714) and idea 3's usage.

**Risks.** Small. The 24-column floor leaves no room for meta in a deep tree:
drop the meta before truncating the description.

## Considered and cut

- **Model-written summaries** of an agent or a turn: needs a model call
  (`$.model`), which the anti-goals forbid.
- **Reaching subagents with the guide** by rewriting the Agent prompt in
  `agent.spawn`: changes the conversation; Findings already parked it for
  Aaron's decision.
- **Auto-injecting last session's notes** at `session.start` or through
  `prompt.context`: changes the conversation without the person asking.
- **Stop or kill an agent from the pane** (`$.turn.abort`, TF 3145): the mod
  would stop being an observer.
- **Collapsing long tool output in place** (`ToolResult` rewrite): the spec's
  first non-goal; idea 9 is the additive subset.
- **Auto-allowing permissions from the pane**: a `tool.check` answer, against
  "never blocks or rewrites".
- **Cross-session compare, charts, a drawn graph**: v1 non-goals with little
  day-to-day value in a 62-column pane.
- **Spinner rewrite** to show the focus line (TF 11203): the band already
  carries it.
- **A placed row at each turn's end** (`$.ui.place`, TF 2638) summarising the
  turn: adds transcript noise; the Timeline's turn header does the job.
