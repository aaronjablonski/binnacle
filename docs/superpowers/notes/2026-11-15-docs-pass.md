## Contradictions

C1. `/mc` is registered without `immediate: true`. Plan Task 5 Behaviour (`/mc` opens the pane); `mod/hooks/register.tsx`.
  - api, "Add a command": a command typed during a turn waits for the turn to end unless registered with `immediate: true`. TF line 1984.
  - A Mission Control pane is mostly wanted while Claude works. Plan should say: register `/mc` with `immediate: true` and `argumentHint: '[close | pin <note>]'`.

C2. `Progress` has a required `label`. Task 5, TASKS section ("a `Progress` (`value: done`, `max: total`)").
  - TF `ProgressProps` (line 8786): `label: string` is required and not blank; `valueText` carries the figure. No doc page mentions Progress; TF is the authority.
  - Plan should say: `Progress({ label: 'Tasks', value: done, max: total, valueText: d + ' of ' + n })`. TF `Elements`: an app only gets `Progress` if it named it in `draws`, otherwise it draws a Box and Text; the surface tests should accept that fallback (the `TASKS d/n` heading already carries the count).

C3. `variant="primary"` on the current tab does nothing for a `plain` button. Task 5 ("hotkeys `1`-`5`, the current one `variant="primary"`").
  - TF `ButtonProps.variant`: "`plain` wins: a plain Button draws the same either way". The hotkey labels `1: Overview` require `plain`. The docs (interface, `hello-tabs`) mark the open tab by `dimColor: tab !== name` on the others.
  - Plan should say: current tab = the others get `dimColor: true` (or the current gets `inverse` via a `Text` child); `variant: 'primary'` only for non-plain buttons such as Pin and Back. Narrow labels (first three letters) still work.

C4. Hotkeys are not universal. Task 5 (`1`-`5`), Task 6 (`l`, `t`), Task 8 (`b`, `p`, `c`), Task 9 README.
  - interface, "Keyboard focus and hotkeys": in VS Code "buttons have no hotkeys"; hotkeys press only while the pane or band has focus; a bracketed button shows no hotkey in the terminal, `plain` shows `1: One`.
  - Plan should say: every hotkeyed button has a label that works without the key; the non-plain `Back`, `Pin`, `Copy result` put the key in the label (`Back (b)`) or become `plain`; the README says hotkeys are terminal and desktop only.

C5. `columns: 62` is a request. Task 5 Behaviour.
  - interface, "Open a pane at the right time"; TF `PaneOpenArgs.columns`: at most 45% of the terminal, at least 24, and a width the user dragged wins in later sessions too. The 24-column "narrow" tests match the floor.
  - Plan should say: views lay out from `e.props.bodyColumns` only, and pass `rows` for the inline seat (K3).

C6. `autoOpen` may not draw. Task 5 ("With `autoOpen`, `session.start` opens it without `focus`").
  - interface, "When a pane waits for a wider terminal": a pane the mod opens by itself (`session.start`, timer, `turn.start`) is placed only at 144+ columns (110 once the user has opened it). Otherwise `$.ui.open` resolves `{ isPlaced: false, reason }` and the pane waits.
  - Plan should say: the test asserts the `$.ui.open` call, not that the pane shows; `isPlaced:false` is not an error; wrap the call in try/catch inside the one `session.start` hook (a throw skips the hook, so `startGuide` and the rest would not run; api, "Add a command" says the same of a throwing `session.start`).

C7. A Button's children can only be strings and `Text`. Task 6 (agent = one Button with a second dim line), Task 8 (step Button with a note on a second line), Task 9 (two-line art Button).
  - TF `ButtonProps.label`: children of strings and `Text` are drawn in place of the label, one press anywhere on them; "any other element is refused". So no `Box` inside a Button.
  - Plan should say: the second line is either a `Text` child beginning `\n` (newline is an allowed control character per TF `CodeProps`; not confirmed for `Text`, so the first test of Task 6 must prove it under `claude plugin test`) or a separate non-pressable `Text` under the Button. Choose one in Task 6 and reuse in 7-9.

C8. `art-<index>` is not a stable key. Task 9 Behaviour.
  - TF `ButtonProps.key`: a surface "finds one again by it after a redraw"; the row's text may change, its address must not. Newest-first means a new artifact shifts every index while one has focus. Duplicate keys are a hard error ("is drawn twice", interface, "Which controls need a key").
  - Plan should say: `art-<stepId>` when set, else `art-<kind>-<hash of ref ?? title>`. Check that `TreeLine.key` (`node-<key>`) is identity, not position.

C9. `$.ui.copy` can fail quietly. Task 8 (`Copy result`) and Task 9 (copy, toast `Copied.`).
  - TF `UiCopyResult`: resolves `{ isCopied: false, reason }` when nothing was copied.
  - Plan should say: toast `Copied.` only when `isCopied`, else toast the reason; pass `surface: press.surface` (Task 8 says `e.surface`, Task 9 omits it).

## Constraints the plan misses

K1. Filter every `ui.render` hook (interface, "Pick where to draw"). The Pane hook begins `if (e.requestId !== PANE) return next(e)`; the band hook uses `{ component: 'AbovePrompt' }`. Task 5 does not say it.

K2. Band rules (interface, "Pick where to draw", "When the user collapses the band"; TF `AbovePrompt`).
  - Return `next(e)` for "nothing to say" (the plan does), and also while `e.props.hasSurvey` is true.
  - Do not wrap `await next(e)` in your own Box: on 2.1.325 each mod gets its own row.
  - A collapsed band still runs the hook (`e.props.isCollapsed`); never make it the only place something shows.
  - Size to `e.props.bodyColumns`, not `viewport.columns`. No Button with a digit hotkey in the band: a bare digit in an empty prompt would press it.
  - `AbovePrompt` is raised on terminal, desktop and mobile only: the Task 5 band tests loop three surfaces, not four.

K3. Narrow terminals (interface, "Open a pane at the right time"; TF `Pane`). Under 110 columns the pane is `placement: 'inline'` above the prompt, `rows` tall (default a third); TF: inline the frame fits the tree. Pass `rows` in `$.ui.open` (for example 14) and read `e.props.scroll.bodyRows`, never `viewport.rows`. Task 8's spacer-based windowing needs a manual look at the inline seat, where a full-height spacer tree could ask for more rows than the layout spares; unit tests cannot show it.

K4. Scrolling and Tab (interface, "What each key does"; TF `SiteScroll`). Task 8.
  - Up and Down scroll only when the tree is taller than the body; focus moves with Tab. The README should say "Tab to a row, Enter to open".
  - `scroll.offset` is read when the hook is asked. The user's wheel or keys re-ask; the engine's own moves on the terminal (keeping a Tabbed-to element in view, a clamp) do not. Tabbing past the last drawn row of a windowed list lands on the spacer until something re-renders. Default `pad` of 20 should be at least `bodyRows`, and "Tab through 25 rows" becomes a manual check.
  - Undrawn rows have no buttons, so Tab and hotkeys see only the window. Spacer: `Box({ height: n })` (TF `BoxProps.height`).
  - A filter or fold press changes the list length: clamp the offset (plan's `windowRows` clamp covers it) or call `$.ui.scroll({ in, to })` (TF 2640-2653).

K5. `$.state` rules for the `ui` atoms (interface, "Keep a value in `$.state`").
  - `ui.render` may read state, never write it. Task 8's "a `ui` stored as `ui-1` is read as the initial value" migration, and any pruning of `openTurns`/`folded`, belongs in `session.start`, `classic.SessionStart` or a press handler.
  - Reads in `ui.render` subscribe: a state write redraws without `$.ui.invalidate`. Only the clock and module variables need invalidate.
  - `openTurns` must be declared in `mod/types/index.d.ts` (validate: "<plugin>.<key> is not declared"); `atom` arguments are string literals held in a `const`.
  - `/clear`, `/resume`, `/branch` reset `$.state` to defaults; `register.tsx` already restores on `classic.SessionStart`, so the new field needs the same default there.

K6. Redraw and clock (interface, "Redraw a site"; TF `invalidate`). `ui.render` runs once per input value (props, width) and repaints reuse the answer, so elapsed text goes stale unless invalidated. Limit: 10 a second, 30 for a shown pane, expanded band and prompt hint; faster calls fold, so a 1 s clock is fine. The timer ends when the module reloads and the new module starts its own: Task 5 starts exactly one `$.clock.every` per module instance in the one `session.start` hook, and the callback itself checks "any agent or step running". An idle session's "ago" text is allowed to go stale.

K7. `Code` limits for Task 8 Detail (TF `CodeProps`).
  - `source` is 100000 characters in total per drawing; tab and newline are the only control characters. Tool results carry CR and ESC (PowerShell, colour): normalise `\r\n` to `\n` and drop other C0 characters before drawing, and share one budget between Input JSON, Change and Result, well under 100000.
  - `format: 'diff'` needs real `@@ -a,b +c,d @@` headers with correct counts; "a diff cut mid-hunk does not parse" and draws as plain code. Compute the counts from the line lists; cut by whole lines and fix the header, never by characters.
  - Use `wrap: 'truncate-end'` where a wrapped line would break the 24-column rule. `path` only infers the language and is never read.
  - VS Code draws `Code` plain (gallery, "Show code and changes"), so colour assertions skip that surface.

K8. Pane focus and keys (interface, "How a pane gets keyboard focus"; TF `PaneOpenArgs`).
  - `focus: true` is a request, granted only with an empty prompt and nothing else focused; `/mc` may open unfocused. The README says Ctrl+X Tab.
  - `autoFocus: true` on one element (first drawn wins; ignored in VS Code) so Enter acts at once.
  - Esc only returns focus unless `closeOnEscape: true` is passed to `open`; `focus`, `closeOnEscape`, `holdToasts` accept only `true` (`false` throws), so build the options object conditionally.
  - `/mc close` calls `$.ui.close({ id: PANE })`; closing an id that is not open is ignored.

K9. A tree with an unknown prop, or a child where none goes, fails the hook and draws nothing (`ui.render hook skipped: returned the wrong shape`; interface, "Build a tree from elements"). `Markdown` takes `text`, not children, and needs a `key` with `onLinkPress`. Tests must run through `claude plugin test`'s real validation, as Task 5 plans.

## Gallery patterns worth reusing

The gallery is a catalogue of single elements in a pane. It has no tabbed pane, band, list-with-detail or tree sample; the closest material is on the interface page and the type file.

G1. Tab row (interface, `hello-tabs`): plain hotkeyed buttons, the inactive dim. Basis for `shell.tsx` (see C3).
```js
const tabButton = (name, label, hotkey) =>
  Button({ key: 'tab-' + name, label, hotkey, plain: true,
    dimColor: tab !== name, onPress: () => { tab = name; redraw() } })
Box({ flexDirection: 'row', columnGap: 3, children: [tabButton('one','One','1'), tabButton('two','Two','2')] })
```

G2. Keyed rows (interface, notes pane): one Box per item, a Button with its own `key`.
```js
...notes.map((note, i) => Box({ flexDirection: 'row', columnGap: 1, children: [
  Button({ key: 'delete-' + i, label: 'x', plain: true, onPress: () => remove(i) }),
  Text({ children: [note] }) ] }))
```
Use `step-<id>`, not the index.

G3. Row text inside a Button (TF `ButtonProps.label` example): one Button, strings plus `Text`, so one press anywhere and a dim part. Use for agent, step, tree and artifact rows (second line: see C7).
```jsx
<Button key={id} onPress={open}>{name} <Text dimColor>2m</Text></Button>
```

G4. Diff and code (gallery, `Code`): copy the shapes for the Change section.
```js
Code({ format: 'diff', source: '@@ -1,3 +1,3 @@\n # Mods\n-A mod is a plugin.\n+A mod is a plugin that runs code.\n Read on.' })
Code({ language: 'javascript', startLine: 1, source: "const name = 'mods'" })
```

G5. Keep-and-add at an engine site (interface, "Change what Claude Code already draws"): `const theirs = await next(e)` inside a Box with your row. Not needed for Pane and band (empty until filled).

G6. The gallery's `/gallery` harness (gallery, "Try a sample"): a throwaway local mod to eyeball a Button with a `\n` child, a Progress, and a 24-column diff before Task 5 commits to them. Do not add it to the repo.
